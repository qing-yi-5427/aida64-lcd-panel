# PC 端性能与资源占用审查

> 历史记录：以下保留当时的方案、环境与验收状态，不作为当前使用说明或性能结论。当前版本请看 [使用指南](../README.md) 和 [验证记录](../VALIDATION.md)。文中的源码行号对应当时版本，后续可能已变化。

审查日期：2026-09-19。对象：曜屏 2.4.1 当前源码与发布目录。此报告只读审查程序；未修改源码、设置或运行状态，未启动窗口/新采集器，未触发 UAC、安装软件或运行压力测试。

## 结论

**结论：当前观察到的 CPU 占用已经很低；内存属于中等体量，还不能称为极轻量工具。**两个 PanelDeck 进程在约 30 秒窗口合计使用约 0.25 CPU 秒，折算整机约 0.052%；私有提交内存合计约 238 MiB。没有发现需要重写整个技术栈的证据，但不能用这个短时低 CPU 结果承诺零游戏影响或长期无泄漏。

现有架构具备轻量常驻工具的基础：复用硬件采集对象、默认 2 秒采样、托盘且无手机时降至 15 秒、完整采集按请求执行、界面隐藏时跳过更新、没有持续动画、没有历史数据无限积累。这里的采样数值是源码默认配置，不是本次进程配置的直接确认。

不过，当前还不能说“所有后台场景都已经优化到位”：**最小化窗口没有被识别为不可见，手机断联后仍可能维持快速采集和界面更新。**这是本次最明确、值得优先修正的问题。界面重复重绘、250 毫秒状态轮询与 GC 模式选择还有改善空间，收益须通过同场景对照验证。

## 可复核证据及优先级

### P2：最小化后未进入后台采样策略

- 位置：[MainForm.cs:25](../PanelDeck.Desktop/MainForm.cs#L25)、[MainForm.cs:102](../PanelDeck.Desktop/MainForm.cs#L102)、[Controller.cs:146](../PanelDeck.Desktop/Controller.cs#L146)。
- 代码事实：`DashboardVisible` 只在 `VisibleChanged` 中取 `Visible`；界面刷新也只判断 `Visible`。普通 WinForms 最小化窗口仍可保持 `Visible=true`，且最小化不等同于 `Hide()`。
- 触发场景：手机已经断联，将 PC 主窗口最小化到任务栏。此时没有人看面板，仍可能按默认 2 秒而非 15 秒采样，并每秒执行界面文本/绘制更新。关闭到托盘的路径有 `Hide()`，能够进入降频。
- 预期影响：在该场景中，修正后采样次数可从理论上限约 30 次/分钟降至约 4 次/分钟，约减少 87%；这些数字是基于配置间隔的代码推导，不是 CPU 降幅。实际周期还包含采集耗时。
- 建议：统一用 `Visible && WindowState != FormWindowState.Minimized` 表示面板正在展示，在可见性和窗口状态变化时同步；后台停止 UI timer 或跳过刷新。手机仍在线时必须保留其正常采样速度。
- 顺便处理：从托盘/最小化恢复时请求一次新样本。目前 `DashboardVisible` 改为 true 不会唤醒 `sampleRequested`，可能要等余下的慢速间隔才刷新。
- 是否值得改：**是，明确且低风险。**本次未操纵用户窗口复现，属于高置信度代码审查发现。

### P3：每秒无条件刷新，增加可避免的绘制与布局分配

- 位置：[MainForm.cs:11](../PanelDeck.Desktop/MainForm.cs#L11)、[MainForm.cs:110](../PanelDeck.Desktop/MainForm.cs#L110)、[UiTheme.cs:107](../PanelDeck.Desktop/UiTheme.cs#L107)。
- 代码事实：窗口可见时每秒刷新两张 CPU/GPU 卡；卡片 `Update()` 总会 `Invalidate()`，自动/息屏按钮也总会 `Invalidate()`。默认硬件每 2 秒采样，相同样本会被再次处理。状态标签、数值、提示文本每次都重新组织。
- [UiTheme.cs:33](../PanelDeck.Desktop/UiTheme.cs#L33) 的文字测量每次创建临时 Font、1×1 Bitmap、Graphics；绘制也创建字体和画刷。相关局部资源采用 `using`，**这里是分配/释放频繁，不是已经证实的 GDI 泄漏**。
- 建议：按样本时间戳和实际状态变化更新控件；只有负载变化才重绘进度条。先减少不必要更新，再考虑缓存 DPI/Font/文本宽度相关测量，避免为小收益引入易错的缓存。
- 预期影响：主要减少窗口可见时的 GDI+ 对象创建、布局和绘制；托盘路径现有提前返回，收益较小。不能凭源码承诺节约固定内存或 CPU 百分比。
- 是否值得改：**是，但排在后台状态修正之后。**

### P3：状态与每条 SSE 连接各自进行 250 毫秒轮询

- 位置：[Controller.cs:89](../PanelDeck.Desktop/Controller.cs#L89)、[LanServer.cs:85](../PanelDeck.Desktop/LanServer.cs#L85)。
- 代码事实：控制器每秒约 4 次重新构造 `PcState`、`ScreenDecision`、`Snapshot`；每条 SSE 流也每秒约 4 次生成 Fresh 快照并拼接状态字符串。最多 4 条 SSE；普通单手机场景是约 8 次逻辑循环/秒，另有 UI timer。这不是测得的硬件唤醒次数，运行时可能合并定时器。
- 已有优点：SSE **不是每 250 毫秒发送 JSON**。仅样本/状态变化或距上次发送 5 秒时才序列化并发送。没有每条连接启动新的硬件采样器。
- 建议：以后可由新样本、屏幕策略变化和连接状态变化通知一个合并的异步事件，SSE 保留 5 秒心跳。单手机负载小，不必为了这点轮询重写网络层。
- 预期影响：减少空闲短生命周期对象与定时任务；对游戏帧率或能耗的改善尚无实测证据。
- 是否值得改：**可优化，非当前性能故障。**

### P3：发布配置启用了 Server GC，建议小范围 A/B 验证

- 位置：[PanelDeck.Desktop.csproj:1](../PanelDeck.Desktop/PanelDeck.Desktop.csproj#L1)、发布文件 `artifacts/PanelDeck-Desktop-2.4.1/PanelDeck.runtimeconfig.json:19`。
- 确认事实：发布配置为 `System.GC.Server=true`，主程序和同一 EXE 的授权采集进程使用相同运行配置。
- 推断：这种低并发桌面工具值得比较 `ServerGarbageCollection=false` 的工作站 GC；不代表 Server GC 必定不合适，也不能把整个进程的工作集归因于 GC。
- **版本限制**：程序为 .NET 10；.NET 9 起 DATAS 默认开启，Server GC 会根据工作负载动态调整堆。因此不能套用旧版“一逻辑核固定一堆”来推算本程序的实际堆数或线程数，也不能保证切换会节省多少 MB。[Microsoft：.NET 10 GC](https://devblogs.microsoft.com/dotnet/preparing-for-dotnet-10-gc/)、[DATAS 文档](https://learn.microsoft.com/en-us/dotnet/standard/garbage-collection/datas)。
- 建议：保留基线包，制作仅 GC 配置不同的候选包，在相同手机连接、窗口状态和采样配置下比较 CPU 增量、私有提交内存、工作集、线程数、采样延迟。最终再决定，不要手工强制 `GC.Collect()` 或定时清空工作集。
- 是否值得改：**值得实验，尚不是已证实的性能缺陷。**

### P3：少量资源可以更明确地释放/复用

- [CollectorService.cs:23](../PanelDeck.Desktop/CollectorService.cs#L23) 每次管道请求重建 ACL，`:26` 使用 `WindowsIdentity.GetCurrent()` 但未显式 Dispose。身份对象在这里无须每个样本获取一次，可在循环外获取 SID，并用 `using` 及时释放身份 token。现状可能产生等待终结器回收的临时句柄，不能据此断言永久泄漏。
- [Controller.cs:154](../PanelDeck.Desktop/Controller.cs#L154) 取消任务并关闭网络/采集资源，但 `sampleRequested` 未显式 Dispose；该对象目前未取 `AvailableWaitHandle`，通常不会创建额外内核等待句柄。完善所有权清理即可，不是主要占用来源。
- [UiTheme.cs:11](../PanelDeck.Desktop/UiTheme.cs#L11) 创建的控件长期 Font，以及 `MetricCard` 替换初始字体，建议在未来字体缓存/控件释放设计中明确所有权；本次没有反复开关设置窗口实验，因此不把它计为已证实的持续泄漏。
- 是否值得改：**可随小修处理，优先级低于前两项。**

## 已经做对、应保留的设计

| 部分 | 代码证据 | 性能含义 |
| --- | --- | --- |
| 硬件对象复用 | `Controller.cs:107,129,150`；`HardwareMonitor.cs:14–17` | 不会每两秒重新打开硬件枚举；采集串行，完成后等待下一周期，慢采集不会积压成无限任务 |
| 只开启所需硬件类别 | `HardwareMonitor.cs:16` | CPU/GPU/内存，以及授权时主板；未开启磁盘、网卡、电池等无关硬件类别 |
| UI 与硬件采集分离 | `Controller.cs:89,106` | 同步驱动读取不在 UI 线程；状态联动不必等待硬件读取完成 |
| 真正隐藏时省绘制 | `MainForm.cs:102` | 托盘无可见主窗时，UI timer 回调立即返回；仍有每秒轻量回调，但没有整页更新 |
| 完整采集按需求发生 | `CollectorService.cs:29–35` | 采集器等待管道连接后才更新硬件；无请求时没有自己的定期硬件采样循环。旧服务即使存在也不会无客户端持续采样 |
| 采集来源避免常态重复 | `Controller.cs:117–132` | 优先会话采集，正常收到完整样本即关闭基础采集器。异常超时才回退；旧服务和会话正常时不同时轮询 |
| 传输和缓冲有边界 | `LanServer.cs:44,78,90`；`CollectorService.cs:49–59` | 请求体限制 1 KiB、SSE 最多 4 路；管道 1.5 秒超时、消息最多 256 KiB；保留当前样本而非无限历史 |
| 网络与管道等待异步 | `LanServer.cs:91–95`；`CollectorService.cs:29,42,51,54` | 不为每次等待长占一个专属忙等线程；线程数量不能直接等同于持续 CPU 消耗 |
| 边框无持续动画 | `BorderlessForm.cs:119–125,188–225` | DWM 圆角设置在建窗时调用；标题按钮按绘制/悬停事件更新，没有常驻动画循环 |
| 设置配对倒计时有边界 | `SettingsForm.cs:37,96–98,126` | 仅开启配对后启动，结束/关闭停止释放；网卡列表在打开设置时获取，不在每秒刷新 |
| 有退出与日志控制 | `Controller.cs:154–159`；`SessionCollector.cs:45–54`；`DiagnosticLog.cs:10` | 退出取消任务；会话采集监视父进程，父进程结束后清理，等待有 5 秒上限；日志约 128 KiB 轮转 |

仍需注意：若硬件驱动同步调用挂起，UI 退出最多先等待采样任务约 3 秒，再等待网络约 4 秒；这类异常退出不是常态运行 CPU 开销。硬件枚举库内部开销和驱动的游戏帧时间影响没有在本次审查中测量。

## 磁盘体积

当前 2.4.1 发布目录共 442 个文件，159,308,441 字节，约 **151.9 MiB**。体积主要来自自包含的 .NET、WindowsDesktop、ASP.NET 运行时；带有约 3.3 MiB 的 PawnIO 安装包。磁盘大小不等于运行时内存；框架文件也不是每个进程全部加载。

这不是“小于 10 MB 的单文件小工具”。如确需缩小下载体积，可提供额外的依赖系统运行时版本，但会增加用户安装前提。现阶段没有证据支持为减小安装包而改写成另一套 UI/HTTP 框架；不要对 WinForms + 反射依赖盲目开启裁剪。

若以“常驻时低 CPU、不会持续刷 UI 或积压任务”为目标，当前隐藏状态表现符合轻量预期；若以“几十 MiB 的极简小工具”为目标，目前没有达到。最合理的下一步是先修最小化判断和无变化重绘，再验证 GC 配置，不是为了一个数字重写产品。
